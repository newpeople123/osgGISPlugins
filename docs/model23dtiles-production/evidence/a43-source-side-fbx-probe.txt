## 2. 为什么这些数可信（三条自检，两条是被"打脸"逼出来的）

- **① 结构**：每个数组 `inflate` 之后长度必须**精确**等于 `arrayLength × elemSize`，否则整条丢弃。
  本文件 2729 个数组全部通过（"失败 0"）——只要偏移或步长理解错一个字节，不可能 2729/2729 全对。
- **② 统计**：非零向量里"不在 1±1 % 单位长度"的条数 = **0**（样本 16 675 068 条非零向量）。
  这一列是**阳性对照的反面**：布局搞错那一版（把 `PolygonVertexIndex` 的头偏移按错的
  名字长度算、并且**没有 inflate**，直接把 zlib 字节当 double 读）实测
  `非单位 = 16 675 068 中的 16.4 M`、零法线"247 916 个"、角点合计 3.36e12——
  一个明显荒谬的数。改成正确布局后非单位归 0，说明现在读的是真向量而不是随机字节。
  **没有这一列，"150 个零"完全可能是解析产物。**
- **③ 配对**：每个含零法线的法线数组都要能对上**同一 mesh** 的 `PolygonVertexIndex`
  （属性在 Layers 之前写出，所以取"最近的前一个"），且**元素数 == 角点数**。
  去重后 7/7 全对上。因此"整面"不是"我假设 3 角点=1 面"，而是按 FBX 自己的
  **负下标多边形边界**算出来的：21 个被触碰的多边形，21 个整面全零，
  且每个都恰好贡献 1 个"末角点"（`零角点里落在多边形末角点上的 = 21`）。
  21×3 = 63 = 零角点数 = 零角点唯一顶点数 → 这 21 个面全是三角形，且面与面之间不共享顶点。

- **对照（拦"恒阳"，不属于上面三条自检）**：同一个脚本跑一个非 FBX 文件
  （`node scripts/fbx_source_normals_probe.js test_assets/t01_plane_curved.obj`）得到
  `Normals 属性命中 0 …零长度 0 …` 并打印"源里没有零法线"、**rc=0**；
  缺参数时 rc=2。也就是说"真源里 63 个零"不是脚本无条件报阳。
  （注意 rc 必须在**没有管道**的情况下取：`node … ; echo rc=$?`，
  带 `| tail` 会拿到 `tail` 的退出码——本轮在别处就踩过这个坑一次。）

## 3. 源侧 → 产物侧的对应（两条独立读路径撞出同一组数）

| 源侧（裸读 + inflate） | 产物侧（FBX SDK → OSG → glTF，`zero_normal_triage.js`） |
|---|---|
| 某 mesh 法线数组 = 14 454 角点，其中 1 个整面全零（角点 33/34/35） | `i952.i3dm#mesh0`、`t162.b3dm#mesh0`、`t166.b3dm#mesh0` 各自**该图元三角形 = 4 818**、**零法线顶点 = 3** |
| 14 454 ÷ 3 = **4 818**（整除，无余数） | 14454/3 与 4818 精确相等；零法线 3 条 = 源侧那 1 个整面的 3 个角点 |

两边用的是**完全不相干**的两条读路径（我们自己的二进制解析 vs FBX SDK 导进 OSG 再写 glTF），
在同一个 mesh 上同时撞上"面数"和"零法线条数"两个数——这是本条取证里最硬的一环。

其余瓦片对不上是**预期**的，不是反例：源里 36 个数组（按内容去重 7 个，其余是逐字节相同的
instance 拷贝），产物侧 26 个瓦片共 195 条，因为瓦片是**按空间切分**几何、并且同一份原型
几何被多个 LOD 复用（`mesh0 v24/v25/v26 × 6`）。例如源里一个 396 角点数组带 24 个零角点，
产物侧若干瓦片报 20 条——20 < 24 正是"该瓦片只切到这份 mesh 的一部分"的形态；
反过来如果写出侧在造零，我们看到的会是**新增**的、源里没有的下标签名。

## 4. 由此**排除**的三条候选

- **写出侧（`Osg2Gltf`/`GltfOptimizer` 的 NORMAL 通路）**：源里本来就有这 63 个零，
  写出侧不需要造。另：`SourceModel.cpp:805-808` 是**逐顶点条件 push**、`:856` 在尺寸不匹配时
  把整条法线数组丢掉——这两条路径要么原样带上、要么整条没有，**造不出 0**。
- **简化器**：`t162`/`t166`/`t699`/`t716` 是 `EXACT_LEAF`（未经简化的源几何拷贝）就带 3 条，
  各条全落在非退化三角形上；本轮源侧再独立确认"整面全零"。
- **A-38 同族（槽里装错数据/未初始化内存）**：那些零是**确定**的、跨瓦片跨 LOD 签名一致的，
  而且源文件里逐字节可复现；A-38 的形态是值随分配器状态变、且污染的是 POSITION 分量。

顺带排除的：**平滑组/重算法线不可能是原因**——`recomputeNormals`（`tools/model23dtiles/main.cpp:164-171`，
走 `osgUtil::SmoothingVisitor`）只在 `-nrm` 下调用（`main.cpp:600-611`），
v15/v17 命令行都没有 `-nrm`，所以产物里的法线就是源法线的忠实透传。
`WB_DUMP_SOURCE` 那个构建侧口子**这个问题不需要了**。

## 5. 仍然没被这份取证覆盖的（不装成已解决）

- 本文件证明的是"源里有 63 个零角点（21 个整面）"，**没有**做逐顶点 join 去证明
  产物 195 条里的每一条都对应源里哪一个（那需要把切瓦/LOD 后的索引反变换回源 mesh 局部号，
  且顶点位置经过了瓦片平移）。能证伪 §3 对应关系的观察是：某个含零法线的产物瓦片，
  其图元来自一个**源里没有零法线**的 mesh。要判这个需要 mesh 级的源↔产物 id 映射，未做。
- `src/osgdb_fbx/fbxRMesh.cpp` 里两条**未证实**的候选机制仍是记录状态（不是结论）：
  `getVertexIndex:74-102` 在不支持的 mapping mode 下静默留 `index=0`，
  `getElement:124-131` 不校验就 `GetDirectArray().GetAt(...)`（FBX SDK 头
  `fbxarray.h:182` 明写"越界不抛错"）。它们能解释" importer 把别的槽的值搬到法线槽"，
  但**与本条的源侧零法线不是同一件事**——源侧零已经独立成立。

## 6. 定级与处置（据此改判）

- 源侧 authored 的零法线（整面三条角点法线同时为 0）→ **不是我们的缺陷**，
  是**输入数据的缺陷 + 我们忠实透传**。本文件头实测 `Creator = FBX SDK/FBX Plugins version
  2016.1.21`（FBX SDK 2016.1.2 写出），**上游是哪个 DCC/哪次导出没证据**，不猜 3ds Max。
- 判据本身仍要有判别力：产物里 55 条落在非退化三角形上 = 可渲染、局部 shading 异常、
  validator 逐条告警；**不触发拒绝发布**（手册的"宁可拒绝发布"针对的是**不可渲染/位置错**
  的产物，这里不属于）。
- 处置改为**写出时修复**：把零长度法线按其所在**非退化三角形的面法线**重算（这三处是整面全零，
  面法线由三个角点位置直接可算，不需要邻接图），而不是按"邻接非退化三角形面积加权平均"
  ——源侧签名说明整面的三条角点法线同时为 0，邻接平均在这里没有可用的非零邻居。
  动手需要构建位（`lugouqiao_v17` 正在跑，并行构建会撞 post-build `z-applocal` 拷贝，MSB3073）。
